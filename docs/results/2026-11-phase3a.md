# Diff-IK Phase 3a results — simulated SO-101, 2026-11-15

**Target:** the so-101 module's `devrel:so101:simulated` arm, which is 5-DOF and kinematic only (an interpolator at `speed_degs_per_sec: 90`, with no dynamics). It runs on a local viam-server from `dev/so101-sim.json`, served for these runs on port 8081 because the MuJoCo machine held 8080. The so-101 module was rebuilt with `make` first, because the checked-in binary predated streamed moves.

**Start pose:** `q0a = (0, 0.3, 0.3, 0.5, 0)` rad. The TCP is 271 mm out and 90 mm up, with the tool pointing forward and down (`o = 0.45, 0, −0.89`).

**Task:** `pointing`, which is the default for a 5-DOF arm, with position as the priority.

**Damping:** `--singular-eps 0.03 --max-damping 0.05`. The rationale is below.

## Damping choice

These come from `testdata/so101.urdf`, sweeping the elbow at `q = (0, 0.3, e, 0.5, 0)`:

| Elbow (rad) | σmin(J_lin) (position level) | σmax(J2·N1) (pointing level) | σmin, 6×5 pose |
|---|---|---|---|
| −1.5 | 0.022 | 0.42 | 0.011 |
| −1.3 | 0.026 | **0.019** | **0.0006** |
| −1.0 | 0.040 | 0.31 | 0.015 |
| 0.0 | 0.084 | 0.60 | 0.061 |
| +0.4 | 0.090 | 0.66 | 0.075 |
| +1.5 | 0.024 | 0.82 | 0.031 |

The position level's weakest σ is only 0.02–0.09 on this arm. With the UR5e's default ε = 0.04, damping would be active whenever the elbow is below about −1.0 rad, which covers a lot of the normal workspace. ε = 0.03 keeps it to the ends of the elbow's range and to the singularity at about −1.3 rad, where σmax(J2·N1) collapses. λmax = 0.05 is half the UR5e default, scaled to the SO-101's smaller σ. The singular sweep is centred at −74° (−1.29 rad), the measured minimum. The spec's first estimate of −1.5 rad came from coarser sampling, and ±0.2 rad around it would cross the ±1.69 rad joint limit.

## Reading the numbers

- **Position priority works as designed.** A pointing target the arm can't reach (an azimuth change) still converges on position exactly. The whole unreachable part is reported as `pointing_residual_deg`, within 0.12° of the geometric prediction `asin(sin 20° · |a_xy|)`, and damping stays at 0. Reachable targets converge on both position and pointing.
- **The CLI circle (22.6 mm) and the bench circle (1.6 mm) measure different things.** The CLI drives the loop with `SetTarget` and no velocity, so it shows the bare P-loop lag, v/K = 50/2 = 25 mm. The bench streams `servo_target`, whose velocity estimate feeds forward. The bench number is the Phase 2 servo path; the CLI number is the Phase 1 baseline on a new arm.
- **The sim flatters tracking.** The simulated arm has no dynamics and only about one tick of streaming lag. A 1.6 mm circle error and 28 ms to first motion are therefore lower bounds, not hardware predictions. Compare the MuJoCo UR5e's 10.5 mm and 81 ms, which include about 240 ms of pipeline lag. The circle's pointing residual comes from geometry (the azimuth follows the target around the base), not from lag.
- **The ramp-stop really decelerates here.** 5.5 mm of travel from 50 mm/s over a 200 ms ramp is close to the ~5 mm of an ideal linear ramp. On MuJoCo it was 9.3 mm, because `arm.Stop` cut the lagged waypoints. That supports the Phase 2 reading: stop smoothness on real hardware depends on the driver's queue, which is still an open item for 3c.

## Finding: other clients can end a servo session

The first bench attempt faulted with `sending joints: arm stream: … context canceled`. The server log shows why: `session liveness expired … stopped_resources: [arm]`. A helper script had moved the arm with `MoveToJointPositions` and disconnected. About 2 s later, viam-server's session safety stopped the arm on that session's behalf. That cancelled the servo's streamed move, and the servo session faulted and stopped, as designed.

This was correct, safe behaviour, and it matters operationally. What was observed: **a client whose session expired after it had commanded the arm ended a running servo session.** This was seen once, on a local viam-server with the simulated arm. Clean disconnects, other session settings and hardware are untested. It's worth noting in the API proposal, for example whether a servo session should own the arm's session or declare exclusive use. The rerun waited for the helper's session to expire and then passed.

## Changes made during Phase 3a beyond the plan

The reviews added or changed these:
- an absolute rank floor of 1e-5;
- dropped pose rows no longer use up the active rows' speed cap;
- roll is removed from the pointing target's advance;
- the leash reach is kept across `SetMotion`;
- reachable-target sampling is bounded;
- `--task` is validated before the singular pre-move;
- golden files are per-architecture.

The spec and plan record each one, apart from the final review's fix: the pose-mode leash now ignores dropped rows, covered by `TestPoseLeashIgnoresDroppedRow`.

The UR5e bit-exact golden guard is recorded for arm64 only (`testdata/golden_ur5e_arm64.json`). On other architectures the test skips, because Go fuses multiply-adds differently there.
