## Tuning findings

1. **Sim streaming latency is about 240 ms.** Measured joints trail `q_cmd` by 11–12 ticks, from cross-correlating the static and circle CSVs. The default `ResyncDeg` allows 3 ticks, so on a moving target `q_cmd` keeps resyncing back to `q_meas` and gives up its lead. `--resync-deg 15` eliminates resyncs and cuts circle error by about 30 %. The loop default is unchanged, because a larger value lets the command run further ahead of a real arm. Decide this per target in Phase 2.
2. **The circle error floor is the P-only loop.** Following a ramp with Gain 2 at 50 mm/s gives v/K = 25 mm of lag. The commanded-side error measured 22.5 mm, and the ~240 ms pipeline accounts for the rest. Target-velocity feedforward (`v = ẋ_target + K·e`) is the fix. It is the natural next step for visual servoing and teleop, where the target moves.
3. **Host load shows up directly in loop timing.** With the sim, scene-camera stream and vision service all on one laptop, p99 tick time ranged from 8 to 33 ms. Overruns then caused the resync storms in static run 2.

## Measurement fixes made during the runs

These are bugs in the CLI metrics, not in the loop.

- **`validate` linear Jacobian check:** it reported 73.7 % because nudging joint 5 (flange roll) moves the flange point only 0.0003–0.005 mm, all from the model offset. Near-zero motion is now skipped below 0.1 mm instead of 0.01 mm.
- **`singular` peak velocity:** it reported 152°/s, which is physically impossible because the sim caps joints at 60°/s. Rows are stamped at tick start but read mid-tick, so after an overrun two stamps sat 2 ms apart. Velocity is now measured over a 10-tick window.
- **Rate bar:** the check failed at a displayed "50.0 Hz", which was really 49.97. A 50 Hz ticker's measured average straddles 50. The bar is now ≥ 49.5 Hz, printed to two decimals.
- **New `--resync-deg` flag:** added for finding 1.
