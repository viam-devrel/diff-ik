# Diff-IK Phase 2 results — MuJoCo sim, 2026-11-15

**Machine:** `mujoco-sim-mac` (part `mujoco-sim-mac-main`) with the vision-pick scene. The arm is `pick-arm`, a UR5e (`viam-labs:mujoco-sim:arm`, `max_joint_deg_s: 60`).

**Deployment:** two entries were added to the machine config:
- local module `diff-ik` → `bin/diff-ik`;
- service `servo` (`rdk:service:motion`, `devrel:diff-ik:servo`, `arms: ["pick-arm"]`).

The module runs inside viam-server next to the sim, so it's co-located as the brief requires.

**Clients:** both connect from the same laptop to viam-server's plaintext loopback listener.
- `clients/python/servo_bench.py`: `--insecure --arm pick-arm --joint-deg-s 60`.
- `clients/ts/smoke.ts`: `HOST=http://localhost:<port>`.

**Start pose:** `[-90, -90, 90, -90, -90, 0]°`, the same as Phase 1. Every session uses `frame: "pick-arm_origin"`.

The two full bench runs agreed to within 7 ms and 0.1 mm. The tables show the second run.

## Latency (unary DoCommand over loopback)

| Metric | Value | Bar |
|---|---|---|
| Command → first joint motion, median of 10 steps of 20 mm | 81 ms | baseline |
| Command → first joint motion, max | 84 ms | baseline |
| `servo_target` round-trip, median | 0.9 ms | baseline |

"Motion" means the first joint sample that moves more than 0.05° from the pre-step pose, polled on a second connection. Roughly 30–40 ms of that is the loop: 0–20 ms waiting for the next tick, plus the 20 ms `armIO` schedules each waypoint ahead. The rest is the sim's streamed-move pipeline taking up the step before the arm moves.

## Stop and dead-man

| Metric | Value | Bar | Result |
|---|---|---|---|
| `servo_stop` round-trip, including the 200 ms ramp | 212 ms | baseline | — |
| `servo_stop` sent → arm stationary | 200 ms | baseline | — |
| Travel after the stop was sent, from 50 mm/s | 9.3 mm | baseline | — |
| Last twist → `stopped_timeout` (timeout 500 ms, ramp 200 ms, 50 Hz) | 750 ms | ≤ 790 ms (timeout + 2 ticks + ramp + 50 ms) | **PASS** |
| Last twist → arm stationary | 725 ms | baseline | — |

The bar measures the `stopped_timeout` transition, which is when `arm.Stop` is issued, rather than the arm actually stopping, because the spec allowed for the sim's streaming lag. The brief's "one loop period plus ramp" works out to 720 ms from the last command (500 + 20 + 200). The arm was stationary at 725 ms, which matches that within polling resolution. The 750 ms state transition reads later because `servo_status` is polled every 20 ms.

**The ramp did not smooth the stop on the sim.** A linear ramp from 50 mm/s over 200 ms should cover about 5 mm, but the arm travelled 9.3 mm, an average of about 46 mm/s. The sim's streaming lag means the arm is still running waypoints queued before the stop when `arm.Stop` cancels the queue. So the ramp's slowing waypoints never execute, and the arm halts abruptly from near full speed. Stop *latency* is short and predictable, but the deceleration is a hard stop. On real hardware that is an `arm.Stop` at speed (see Open items).

## Circle with feedforward (50 mm radius at 50 mm/s, 2 laps, pose mode, 50 Hz from the client)

| Config | Mean error | Max error | Resyncs / overruns | Phase 1 mean (same config) | Bar |
|---|---|---|---|---|---|
| default `resync_deg` | 10.5 mm | 11.4 mm | 0 / 0 | 45.8 mm | report |
| `resync_deg: 15` | 10.6 mm | 11.4 mm | 0 / 0 | 31.6 mm | ≤ 22.1 mm: **PASS** |

The error is the measured flange position (`EndPosition` on a second connection) against the circle's commanded point at that moment.

**Feedforward cut the tracking error by 77% at the default setting and 66% at `resync_deg: 15`.** The measurement method differs from Phase 1: Phase 1 compared the loop's per-tick FK(q_meas) with its own target, while Phase 2 compares a client-polled `EndPosition` with the ideal circle. Both measure the arm's actual pose against where it should be, but the comparison isn't strictly like-for-like.

The remaining ~10.5 mm is nearly constant. At 50 mm/s that corresponds to ~210 ms of lag, a little below the ~240 ms Phase 1 measured for the sim's streaming pipeline. So the arm follows the commanded trajectory with a time lag from the pipeline, not a lag from the control law.

A repeat during a demo run on a busier laptop gave 12.4 mm mean with about 25 overruns, against 0 here, so host load shows up directly in tracking.

Phase 1 needed `resync_deg: 15` to stop resync thrash. With feedforward the default needs no tuning: the resync count is 0 either way.

## Findings

1. **Feedforward removes the control-law lag on moving targets.** Phase 1's P-only loop trailed a moving target by v/K = 25 mm on top of the sim lag. With the target-velocity estimate fed forward, only the sim's pipeline lag remains. That matters for the brief's use cases, teleop and visual servoing. Whether it beats the builtin `Move` is untested until Phase 4's comparison.
2. **Unary DoCommand isn't the bottleneck on loopback.** A `servo_target` round-trip takes 0.9 ms, and 50 Hz client streams held 50.1 Hz with no overruns. The ~80 ms command-to-motion time is in the arm pipeline, not the API. A streaming RPC would matter more over a real network. That's still to be measured.
3. **Stopping is fast, but on the sim the ramp is cosmetic.** Stop latency equals the ramp (200 ms). Because `arm.Stop` cancels the waypoints queued during the streaming lag, the arm halts from near full speed instead of decelerating (9.3 mm travelled against ~5 mm for a true ramp).

## Fixes made during the run

- **Bench stationary check:** it compared consecutive polls about 1 ms apart, so a moving arm read as stopped ("1 ms" to stationary). It now requires 100 ms within 0.05°.
- **TypeScript plaintext dial:** `createRobotClient` reports failure for a working direct gRPC dial, because `isConnected` checks the WebRTC ICE state. The smoke client now calls `RobotClient.dial` for direct connections.
  - The SDK also rejects direct hosts that don't contain "local", so use `localhost`, not `127.0.0.1`. Both are SDK quirks worth reporting upstream.
